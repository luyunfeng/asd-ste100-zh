# 评测第二轮：计算机领域适配

方法：12 个样本全部做受控改写，按 rubric.md 四维打分（各 0-3，满分 12）。改写者：本技能规则 + 术语表；评分者：同一模型按评分标准独立复核。

S1-S5 完整对照见 [skills/asd-ste100-zh/examples/before-after.md](../skills/asd-ste100-zh/examples/before-after.md)。S6-S12 改写如下。

## S6 · 报错信息

- 改写：「磁盘空间不足。原因未查明。建议操作：清理日志文件。清理前先确认要删除的文件范围。」
- 说明：原文没有给出路径和数量，受控改写**不能虚构数值补具体性**——只能把含糊结构化。信息量不足是原文的问题。

## S7 · 工具描述

- 改写：「本 CLI 采集日志，支持多种数据源。支持哪些来源，运行 `--list-sources` 查看。」
- 说明：原文「一站式/海量/各种场景」无信息单元，删除；支持的来源列表原文没有，不编造，指向可验证处。

## S8 · 代码评审意见

- 改写：「建议给 `getUserProfile` 加缓存：当前每次请求都查数据库，加缓存后重复请求不再查库。预期收益需要压测确认。」
- 说明：保留原文的不确定度（「应该能提升」→「预期收益需要压测确认」），不把猜测写成结论。

## S9 · agent 间指令

- 改写：「任务：升级 `go.mod` 中的全部依赖。步骤：1. 运行 `go get -u ./...`。2. 运行 `go test ./...`。3. 全部通过：提交并合并到 main。4. 有失败：停止，把失败的测试名发回本会话讨论。」
- 说明：原文「看看有没有什么问题」无验收标准，改写把「通过」定义为「全部测试通过」，条件挂到动作上。

## S10 · 部署步骤

- 改写：「回滚步骤：1. 确认当前版本号。2. 恢复上一版配置。3. 重启服务。4. 观察 10 分钟，确认错误率回到基线。」（命令按实际环境替换）
- 说明：原文信息完整但句式含混；只做结构化，不添加原文没有的命令。

## S11 · README 段落

- 改写：「本项目是一个服务治理工具。」
- 说明：原文全部是空壳修辞，无信息单元可保留。改写后只剩一句——**这暴露的是原文信息量为零**，受控改写只做减法，不负责补充内容。

## S12 · system prompt 片段

- 改写：「回答用户的问题。要求：1. 用正式书面语。2. 覆盖问题的各个方面。3. 在抽象论点处给出例子。」
- 说明：删除「比较/一些/适当地」等缓冲词，要求本身全部保留。

## 本轮发现

- **发现 A（重要）**：含糊的原文（S6/S7/S11）不能靠改写变具体——受控改写只消除歧义、不虚构事实。这三例的「术语正确」分受限来自原文信息量，不是规则缺陷。
- **发现 B**：S9 类 agent 指令收益最大（+6）：「看看有没有什么问题」这类验收含糊是 agent 失误的主要来源。
- **发现 C**：S4/S11 术语维度 2 分封顶：README 类文本的可读性依赖具体产品事实，规则只能保证不混用，不能提供内容。
- 规则与术语表**不需要修改**：所有扣分点都归因于样本原文本身，没有暴露规则的语义缺陷。进入第三轮（机器检查 + 回归）。
